## Docker и контейнеры
1. **Что такое Docker и зачем он в DevOps?** Платформа для упаковки приложения вместе с его окружением в контейнер. Контейнер одинаково работает на любой машине, что упрощает поставку и тестирование.
2. **Образ и контейнер.** Образ — неизменяемый шаблон (файловая система и настройки). Контейнер — запущенный экземпляр образа.
3. **Зачем FROM в Dockerfile?** Задаёт базовый образ, на котором строится новый.
4. **RUN и CMD.** RUN выполняется при сборке образа и создаёт слой. CMD задаёт команду по умолчанию, которая выполняется при запуске контейнера.
5. **EXPOSE.** Документирует порт, который слушает приложение. Сам по себе порт наружу не публикует; для этого нужен `-p` или `ports:` в compose.
6. **WORKDIR.** Задаёт рабочий каталог для последующих инструкций и команды запуска.
7. **COPY и ADD.** COPY просто копирует файлы. ADD умеет дополнительно распаковывать архивы и скачивать по URL, поэтому для обычного копирования используют COPY.
8. **Многоэтапная сборка.** Первый этап содержит JDK и Gradle для сборки, второй — только JRE и JAR. Итоговый образ меньше и безопаснее.
9. **docker build.** Собирает образ по Dockerfile. Пример: `docker build -t zhambyl-osken-zharqynuly-student-api:v1.0-id37437 .`
10. **Docker volume и его важность для PostgreSQL.** Volume хранит данные вне контейнера. Без него данные БД пропадают при удалении контейнера.
11. **Docker network и volume.** Network отвечает за связь между контейнерами по сети. Volume отвечает за хранение данных.
12. **docker stop и docker rm.** stop останавливает работающий контейнер, rm удаляет остановленный контейнер.
13. **Docker Compose.** Инструмент для описания и запуска нескольких контейнеров одной командой (`docker compose up`). Удобен для связки приложения и БД.
14. **Как запустить контейнер с пробросом порта 8080.** `docker run -p 8080:8080 <image>`: порт 8080 хоста направляется на порт 8080 контейнера.
15. **Просмотр логов контейнера.** `docker logs <container>` или `docker compose logs app`.
16. **Выполнение команды внутри контейнера.** `docker exec -it <container> sh`.
17. **Health check и готовность PostgreSQL.** Health check периодически выполняет проверку (здесь `pg_isready`). Статус healthy показывает, что БД готова принимать подключения, а не просто запущена.
18. **Почему подключение по имени сервиса (db), а не localhost.** Внутри контейнера localhost указывает на сам контейнер приложения. Имя сервиса Compose разрешается в IP контейнера БД через внутреннюю сеть.
19. **Как передавать данные БД в контейнер.** Через переменные окружения из файла `.env`, который не хранится в Git.

## Git и GitHub
20. **Git и GitHub.** Git — система контроля версий, работающая локально. GitHub — хостинг удалённых репозиториев на базе Git.
21. **git commit.** Фиксирует проиндексированные изменения в истории репозитория с сообщением.
22. **git add.** Переносит изменения в staging area (индекс), готовя их к коммиту.
23. **git status.** Показывает, какие файлы изменены, проиндексированы или не отслеживаются.
24. **git init.** Создаёт пустой Git-репозиторий в текущей папке (каталог `.git`).
25. **Рабочая директория, staging area, repository.** Рабочая директория — файлы на диске. Staging area — изменения, выбранные для коммита. Repository — сохранённая история коммитов.
26. **Ветка и зачем она нужна.** Ветка — независимая линия разработки. Позволяет работать над функцией, не трогая main.
27. **Как создать и переключиться на новую ветку.** `git switch -c feature/zhambyl-osken-zharqynuly-crud` (или `git checkout -b ...`).
28. **git merge и git rebase.** Merge объединяет ветки коммитом слияния и сохраняет историю. Rebase переписывает коммиты поверх другой базы, создавая линейную историю.
29. **Что такое merge conflict и почему он возникает.** Конфликт возникает, когда две ветки меняют одну и ту же строку разными способами; Git не может решить сам.
30. **Как разрешить конфликт в README.md.** Открыть файл, удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>`, оставить нужный текст, затем `git add README.md` и `git commit`.
31. **git fetch и git pull.** Fetch загружает изменения из удалённого репозитория без слияния. Pull делает fetch и сразу merge (или rebase).
32. **git push.** Отправляет локальные коммиты и ветки в удалённый репозиторий.
33. **Git commit и Git tag.** Commit — снимок изменений с уникальным хешем. Tag — постоянная метка на конкретном коммите, обычно для версии (например, v1.0-id37437).
34. **Git tag для версии.** Tag фиксирует точку релиза, по которой можно вернуться к конкретной версии.
35. **Почему сообщения коммитов должны быть осмысленными.** Они помогают понять историю изменений, искать ошибки и вести аудит.
36. **.gitignore.** Список файлов и папок, которые Git не должен отслеживать (сборка, IDE, секреты).
37. **Почему нельзя коммитить пароли и .env.** Всё, что попало в историю Git, остаётся в ней даже после удаления, и утечка компрометирует сервисы. Секреты передают через переменные окружения и секретные хранилища.
38. **Локальный код отличается от GitHub.** Выяснить через `git status`, `git log` и `git diff origin/main`. Затем безопасно синхронизировать: сохранить свои изменения коммитом, выполнить `git pull --rebase`, разрешить конфликты, проверить и отправить `git push`. Не использовать `--force` без необходимости.

## Linux и Bash
39. **Что такое Linux и почему он важен в DevOps.** Открытая ОС на базе ядра Linux. Большинство серверов, контейнеров и CI-агентов работают на Linux, а управление ими ведётся через терминал.
40. **Shebang #!/bin/bash.** Первая строка скрипта, которая указывает ОС, каким интерпретатором выполнять файл.
41. **Как сделать скрипт исполняемым.** `chmod +x script.sh` (в проекте после настройки прав: `chmod 744`).
42. **Что делает chmod.** Меняет права доступа к файлу (чтение, запись, выполнение) для владельца, группы и остальных.
43. **Что означает права 755.** Владелец: rwx (7). Группа: r-x (5). Остальные: r-x (5).
44. **pwd.** Выводит путь текущей рабочей директории.
45. **Абсолютный и относительный путь.** Абсолютный начинается с `/` и указывает полный путь. Относительный отсчитывается от текущей директории, например `../logs`.
46. **Как проверить свободное место на диске.** `df -h`.
47. **free -h.** Показывает объём оперативной памяти и swap в удобном виде (Гб/Мб): всего, занято, свободно, в кэше.
48. **mkdir и mkdir -p.** mkdir создаёт одну папку. `-p` создаёт всю цепочку вложенных папок и не падает, если папка уже есть.
49. **Как создать пустой файл.** `touch file.txt`.
50. **cp и mv.** cp копирует файл, оставляя оригинал. mv перемещает или переименовывает, оригинала не остаётся.
51. **Как вывести последние пять строк лога.** `tail -n 5 file.log`.
52. **Как искать слово в файле.** `grep 'слово' file` (например, `grep 'Zharqynuly' log`).
53. **Как вывести скрытые файлы.** `ls -la` (файлы, начинающиеся с точки, видны с `-a`).
54. **Как передать аргументы скрипту.** Указать после имени: `./script.sh arg1 arg2`. Внутри скрипта: `$1`, `$2`, `$@`, количество — `$#`.
55. **Как просмотреть процессы и найти процесс Java.** `ps -ef` или `ps aux`, затем `ps aux | grep -i java`.
56. **Процесс Linux.** Запущенная программа с уникальным PID, которой выделены ресурсы системы.
57. **Как найти и завершить процесс по PID.** `ps -p <PID>` для поиска, `kill <PID>` для завершения (при необходимости `kill -9 <PID>`).
58. **> и >>.** `>` перезаписывает файл выводом команды. `>>` дописывает вывод в конец файла.
59. **Поиск фамилии в логе и сохранение результата.** `grep 'Zharqynuly' logs/....log > logs/Zhambyl_Osken_Zharqynuly_log_analysis.txt`.

## Jenkins и CI/CD
60. **Что такое Jenkins job.** Настроенная задача сборки: откуда брать код, какие шаги выполнять, какие триггеры запуска.
61. **Что такое Jenkinsfile.** Файл в репозитории, который описывает стадии pipeline как код.
62. **Declarative и Scripted Pipeline.** Declarative — структурированный синтаксис с блоками `pipeline`, `stages`. Scripted — полностью программный Groovy, гибкий, но сложнее.
63. **Checkout.** Стадия, которая получает исходный код из репозитория (здесь GitHub).
64. **Build.** Стадия компиляции приложения (здесь `gradlew compileJava`/`clean build`).
65. **Test.** Стадия автоматических тестов. Если тесты падают, pipeline останавливается.
66. **Остановка при падении тестов.** Ошибка в шаге `sh` завершает стадию с ошибкой, и последующие стадии не выполняются.
67. **Что происходит при падении стадии.** Pipeline помечается как FAILED, последующие стадии пропускаются, блок post failure выполняется.
68. **Что показывает Console Output.** Полный журнал выполнения: команды, их вывод, ошибки, время, имя студента.
69. **Зачем Jenkins нужен агент с Docker.** Сборка образа требует доступа к Docker daemon на агенте.
70. **Controller и agent.** Controller управляет задачами и интерфейсом. Agent выполняет фактическую работу сборки.
71. **Jenkins Credentials.** Безопасное хранилище паролей, токенов и ключей. В Jenkinsfile на них ссылаются по ID, сами значения не видны в логах.
72. **Как Jenkins получает код из приватного GitHub.** Через учётные данные (token или SSH-ключ), сохранённые в Jenkins Credentials.
73. **Build trigger и webhook.** Триггер запускает pipeline. Webhook — GitHub отправляет Jenkins HTTP-уведомление при push, и сборка стартует сразу.
74. **Continuous Integration (CI).** Практика частого слияния кода в общую ветку с автоматической сборкой и тестами.
75. **CI и Continuous Delivery/Deployment.** Delivery — код всегда готов к выпуску, но выпуск запускается вручную. Deployment — автоматический выпуск в продакшен после успешных проверок.
76. **Зачем тесты до деплоя.** Чтобы ошибки ловились до попадания в продакшен, а не после.
77. **Почему Docker-стадия отделена от Build.** Если образ не собирается, ошибка локализуется: код компилируется, но проблема в Dockerfile или окружении агента.

## Ситуационные вопросы
80. **Ваш Spring Boot контейнер не подключается к PostgreSQL.** Проверить `docker compose ps` (статус db = healthy), `docker compose logs app`, переменные через `docker compose config` (без вывода секретов), убедиться, что URL использует `db`, а не `localhost`, и что пароль совпадает.
81. **Pipeline собирает приложение, но падает при создании образа.** Открыть Console Output стадии Docker Build, проверить наличие Dockerfile, доступность Docker daemon на агенте, права пользователя jenkins в группе docker, существование базового образа и ошибки шагов COPY (пути).
82. **Как исследовать упавшую сборку Gradle в Jenkins.** Открыть Console Output, найти первую строку с ошибкой (`FAILURE`, `error:`), проверить, какая задача упала, при необходимости запустить `./gradlew build --stacktrace` локально и посмотреть отчёты в `build/test-results`.
